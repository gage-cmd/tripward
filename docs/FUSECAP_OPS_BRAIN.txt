 Executive product brief
 A local safety envelope for unattended and high-autonomy coding-agent sessions.


 One-sentence promise
      A local circuit breaker for coding agents: it stops runaway sessions,
      protects the repository, and produces a receipt explaining exactly what
      happened.
           FIELD                    DECISION

           Problem                  Agents can repeat failing actions, churn files, expand work, invoke dangerous commands, consume quotas, and
                                    spend observable API dollars while the user is absent.

           Initial buyer            Solo developer or tiny team using Claude Code frequently, especially unattended, with meaningful code or API
                                    exposure.

           Initial surface          Claude Code launched with a project or user policy; local runtime and local evidence store.

           Core loop                Configure policy → checkpoint → observe → allow/warn/block/terminate → inspect receipt → restore or resume.

           Paid value               Behavioral detection, durable history, notifications, multiple/concurrent runs, CI, and shared team policy.

           Not the promise          Not a universal hard-dollar cap, not a new model, not a compliance certificate, and not a replacement for native
                                    sandboxing.

           Business status          Problem demand is credible; recurring willingness to pay is not proven. Build only enough to ask for money.



 North-star outcome
 A developer becomes comfortable starting a bounded agent run and walking away because the limits are explicit, the enforcement is
 local, and the recovery path is reversible.

 Product equation
            TRUST = enforceable limits + honest uncertainty + reversible recovery + evidence

            A control that cannot be enforced must be labeled advisory. A cost that cannot be observed must not be
            presented as actual spend. A restore operation that can lose preexisting work must not ship.

 Product principles and non-goals
 Use these rules to resolve design and engineering tradeoffs.


           PRINCIPLE                          ENGINEERING CONSEQUENCE

           Local first                        Raw prompts, code, tool arguments and secrets remain on the machine unless the user explicitly opts into a
                                              later service.

           Deterministic before intelligent   Hard stops begin with rules whose behavior can be tested. Learned judgment begins in shadow mode.

           Evidence before verdict            Every warning or trip points to the exact events and policy version that produced it.

           Reversible by construction         Preserve preexisting work; never make automatic destructive recovery decisions.

           Fail visibly                       If a required hook, daemon, sandbox or checkpoint is unavailable, show that protection is degraded before
                                              the run.

           No fake precision                  Costs are actual only when provider usage is observable; otherwise label list-price estimate or unavailable.

           Minimum privilege                  Request only the filesystem, network and provider access required for the configured policy.

           Progressive enforcement            New behavioral rules observe first, warn second and block only after demonstrated reliability.

           Platform complement                Use native sandboxing and permissions; do not weaken or pretend to replace them.



 Explicit non-goals for v1
 • Cursor parity.

 • Universal LLM gateway or credential vault.

 • Remote command execution from a phone.

 • Enterprise identity, SSO, SCIM or compliance claims.

 • Automatic AI-written remediation of repository damage.

 • Guaranteed detection of every loop or harmful action.

 • Replacement for Git, backups, Claude Code permissions or native sandboxing.

 • Storing full prompts, completions, file contents or secrets in a hosted service.

 PRD overview
 The initial product is a small trusted loop: protect, detect, explain, recover, repeat.


           FIELD                      V1 DECISION

           Objective                  Prove that developers will repeatedly route real Claude Code runs through a local safety envelope and pay for
                                      behavioral intelligence/history.

           User promise               Set boundaries once; receive visible protection on every eligible run; preserve existing work; know why
                                      intervention occurred.

           Platform                   macOS first; Linux next. Claude Code first. Git repository required for recovery features.

           Interface                  CLI-first with local HTML receipt/dashboard. No cloud account required for free local use.

           Persistence                Local SQLite or append-only event store; optional encrypted sync is a later paid capability.

           Distribution               Signed binary/package plus Claude Code plugin/hooks; reversible installer and diagnostic command.

           Success window             Technical spike in 72 hours; paid validation in 14 days; retained-use proof within 45 days.



 Primary workflow
           #       STAGE            SYSTEM BEHAVIOR

           1       Install          Verify prerequisites and show exactly what configuration will change.

           2       Protect          Select a preset or create project policy; run in shadow mode initially.

           3       Preflight        Check Git state, hook registration, policy validity, sandbox posture and storage health.

           4       Checkpoint       Record repository HEAD, index, working tree state and FuseCap-owned recovery reference.

           5       Run              Launch or attach to supported Claude Code session; ingest hook lifecycle events.

           6       Decide           Evaluate deterministic policies before actions and behavioral detectors after observations.

           7       Trip             Warn, ask, block a tool, or terminate according to policy and capability.

           8       Receipt          Seal a local record containing scope, events, trigger, affected files and confidence.

           9       Recover          Show diff; restore only selected agent-created changes after explicit approval.

           10      Resume           Start a new/resumed session with a deliberate policy adjustment and linked receipt.

           GROUP                   FIELDS

           privacy                 event detail, hashing, retention, receipt redaction, optional sync



 Default presets
           PRESET                 DEFAULT INTENT

           Observe                No blocking except known catastrophic commands; collect seven days of local evidence.

           Standard               90 minutes, 150 tools, exact repeat 5, subagents 8, protected secrets, ask on risky commands.

           Overnight              60 minutes, 100 tools, subagents 4, strict sandbox required, block risky network/commands, checkpoint mandatory.

 Trip lifecycle and user experience
 Intervention must be understandable in seconds and recoverable without panic.


           STATE                        MEANING

           ARMING                       Validate policy, runtime, Git state and hooks.

           SHADOW                       Observe behavioral rules without blocking.

           PROTECTED                    Mandatory components healthy; active enforcement.

           DEGRADED                     One or more controls unavailable; show exact missing coverage.

           WARNED                       Risk threshold met; session continues and receipt records warning.

           AWAITING_APPROVAL            Pending action blocked until local user response or timeout.

           TOOL_BLOCKED                 One tool action denied; model may adjust and continue.

           STOPPING                     Graceful stop requested; wait bounded interval.

           TERMINATED                   Supervisor ended process; preserve events and checkpoint.

           COMPLETED                    Normal session end with clean or warned receipt.

           RECOVERY_REVIEW              User comparing pre-run and current state.

           RESTORED                     Selected run-attributed changes reversed and recovery receipt created.



 Trip screen must show
 • The exact policy and threshold that fired.

 • Whether the pending action executed.

 • The last meaningful progress signal.

 • A compact repeated sequence or relevant command/file evidence.

 • Repository state and whether preexisting changes are safe.

 • Options: inspect, continue once, change policy and resume, end, or review recovery.

 • Cost as actual/estimate/unavailable with source and confidence.

 Git checkpoint and recovery design
 Preserve the user's starting state and make every recovery operation explicit.


 Preflight algorithm
           #     STEP                    REQUIREMENT

           1     Verify repository       Resolve canonical root; reject ambiguous nested repositories unless selected.

           2     Capture identity        Record HEAD, branch/detached state, remotes as redacted fingerprints and worktree path.

           3     Inventory state         Capture staged, unstaged, untracked and ignored-state metadata without ingesting secret contents.

           4     Preserve user work      Create a FuseCap-owned recovery object/worktree strategy that does not overwrite index or working tree.

           5     Validate restore        Perform a dry comparison and ensure recovery references are readable before launching.

           6     Begin watcher           Attribute subsequent changes using event time plus Git reconciliation; label uncertain attribution.



 Recovery rules
 • Never run a broad destructive Git reset.

 • Never silently stash or commit user work.

 • Never delete untracked files without an itemized preview and confirmation.

 • Never claim perfect attribution when external editors or processes changed the repository concurrently.

 • Prefer an isolated worktree for unattended high-risk runs when technically compatible.

 • Recovery must create its own receipt and be undoable when practical.

 • If repository state changes outside the observed session, disable one-click restore and guide manual review.

 Definition of safe restore
            A restore is safe only when preexisting staged, unstaged and untracked user work
            remains byte-for-byte available; the user previews affected paths; the operation is
            scoped to selected agent-attributed changes; and the result is verified after
            application.

 System architecture
 Keep enforcement local; make optional cloud features metadata-minimal.


           COMPONENT                     RESPONSIBILITY

           CLI and installer             Setup, policy commands, launch, status, receipts, diagnostics, update and uninstall.

           Claude adapter                Installs/validates hooks, maps lifecycle payloads, reports supported coverage and version compatibility.

           Process supervisor            Starts session, maintains PID tree, timers, graceful stop and force termination.

           Policy engine                 Pure deterministic evaluator for pre-action and cumulative limits.

           Behavior engine               Streaming feature extraction, shadow judgments, confidence and detector versioning.

           Repository guard              Git snapshot, mutation reconciliation, diff statistics and recovery plans.

           Event journal                 Append-only local events; sequence IDs, monotonic timestamps and crash recovery.

           Receipt builder               Compiles redacted evidence, integrity digest and local HTML/JSON outputs.

           Local dashboard               Loopback-only UI for active runs, policies, receipts, recovery and history.

           Notification adapters         Desktop first; optional user-configured webhook/Slack later.

           Optional cloud                Account, billing, encrypted metadata sync and team policy distribution; never required for enforcement.



 Trust boundaries
 Claude Code → signed/validated hook invocation → local adapter → append-only journal → policy/behavior evaluation → decision
 returned to hook or supervisor. Repository access remains local. Optional cloud receives only explicitly enabled, schema-validated
 metadata after local redaction.


 Suggested implementation
 A single cross-platform systems binary (Rust or Go) is the preferred long-term core for process supervision, local storage and
 distribution. A thin plugin/configuration layer integrates Claude Code. A local web UI can be embedded assets. The 72-hour spike may
 use the fastest safe language, but production language is selected by an ADR after installer, process-tree and hook latency tests.

 Assign an increasing local sequence number inside each run. Persist a pending tool decision before returning allow/deny. Use
 monotonic time for thresholds and wall time for display. Event ingestion must be idempotent using adapter event ID plus payload digest.
 On restart, mark incomplete actions unknown rather than assuming success.

 Policy engine mechanics
 Hard stops must be fast, deterministic, testable, and independent of an LLM.


 Evaluation order
           ORD     LAYER                     DECISION
           ER

           1       System safety             Corrupt policy, unavailable required journal, invalid scope or disabled mandatory protection →
                                             deny/stop.

           2       Organization minimum      Later signed minimums may only be tightened downstream.

           3       Protected resource        Secret paths, forbidden write roots, command patterns and domain rules.

           4       Cumulative limits         Elapsed time, tool totals, per-tool totals, subagent counts, mutation limits and observable spend.

           5       Exact behavior            Normalized repeated event/action threshold.

           6       Behavioral signals        Shadow/warn/ask unless detector is explicitly promoted.

           7       Default                   Apply policy default; v1 default is ask or native behavior, never silent broad allow.



 Decision object
 decision_id; run_id; event_id; policy_digest; evaluator_version; matched_rule_ids; action
 (allow/warn/ask/deny/graceful_stop/terminate); reason_code; display_reason; evidence_refs; decision_time_ms; expires_at;
 override_allowed; override_scope; and integrity_digest.


 Performance targets
 • P95 deterministic hook decision under 35 ms on supported local machines.

 • No network dependency in the critical allow/deny path.

 • Journal append completed before returning an irreversible allow.

 • One crashing detector cannot disable deterministic controls.

 • Policy compilation rejects unknown fields unless schema explicitly permits forward compatibility.

 • All thresholds and normalizers covered by table-driven and property-based tests.
